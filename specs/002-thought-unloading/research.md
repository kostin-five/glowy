# Research: Разгрузка мыслей

## Decision 1: AI endpoint возвращает черновики, но не сохраняет их

**Decision**: `/mind-hub` и `/mind-hub/public` возвращают `reply`, `drafts` и limit metadata.
Создание выполняется существующим Task API после frontend-подтверждения.

**Rationale**: Это напрямую выполняет правило явного пользовательского контроля, сохраняет
backend-валидацию создания задач и не требует нового persistence flow.

**Alternatives considered**:

- Сохранять скрытую задачу со статусом draft: требует migration и создаёт серверные данные до
  согласия пользователя.
- Добавить отдельный confirm endpoint в AI route: дублирует существующий Task API и смешивает AI
  orchestration с CRUD задач.

## Decision 2: Черновик — TaskDraft без database id

**Decision**: Backend возвращает существующие поля будущей задачи без `id`, `completed`, `userId`
или persistence metadata. Frontend добавляет только локальный ключ карточки.

**Rationale**: До подтверждения сущность не является задачей и не должна выглядеть сохранённой.
Форма полностью совместима с существующим `TaskDraft` и `createTask`.

**Alternatives considered**:

- Возвращать fake numeric ids как сейчас для demo: смешивает несохранённое состояние с моделью
  задачи и может случайно попасть в store.
- Создать новую серверную таблицу drafts: не нужна для ограниченного session-only scope.

## Decision 3: Ответ и предложение действия независимы

**Decision**: `reply` нормализуется независимо от наличия drafts. AI prompt требует коротко
ответить пользователю и отдельно предложить draft только при явном или уверенном actionable
намерении.

**Rationale**: Пользователь сначала получает помощь, а карточка действия остаётся отдельным
выбором. Текущий parser теряет reply при наличии tasks, что нужно исправить.

**Alternatives considered**:

- Генерировать второй AI-ответ для разговора: удваивает задержку и стоимость.
- Собирать reply только на frontend: даёт шаблонные ответы без контекста пользователя.

## Decision 4: Ошибочный payload не превращается в задачу fallback-парсером

**Decision**: При недоступности provider или повреждённом JSON вернуть безопасный ответ/ошибку и
пустой список drafts. Детерминированная обработка известных корректных формулировок может
сохраниться как часть parser service, но не должна записывать данные.

**Rationale**: Эвристическое создание черновика из любого текста повторяет исходную проблему и
может предложить бессмысленную задачу из обычного вопроса.

**Alternatives considered**:

- Продолжить `parseMindHubFallback` для любого сбоя: повышает availability, но снижает доверие и
точность intent detection.

## Decision 5: Защита подтверждения на уровне UI и существующего API

**Decision**: Карточка блокирует повторное подтверждение во время запроса, после успеха удаляется,
а Task API атомарно создаёт задачу с nested subtasks существующим запросом.

**Rationale**: Закрывает реальный double-click сценарий без migration и нового idempotency store.

**Alternatives considered**:

- Полная idempotency между перезапусками через новый ключ в БД: полезна шире, но требует schema
  change и отдельного согласования.

## Decision 6: Существующие автоматические actions отключаются

**Decision**: Mind Hub больше не выполняет `actions.updateTaskDate`. Запросы на изменение
существующей задачи получают разговорный ответ без mutation.

**Rationale**: Конституция запрещает любые скрытые изменения, а текущая задача проектирует
подтверждение только для создания task draft.

**Alternatives considered**:

- Добавить второй тип update draft: расширяет scope и требует отдельного UX подтверждения для
  каждой операции.

## Decision 7: Аналитика фиксирует только подтверждение

**Decision**: После успешного сохранения вызывается consent-aware событие
`ai_draft_confirmed` без payload с текстом.

**Rationale**: Событие уже зарезервировано roadmap для v2.2 и измеряет полезное действие, не
раскрывая личные данные.

**Alternatives considered**:

- Отправлять тип/категорию/название draft: повышает детализацию, но нарушает privacy boundary.
