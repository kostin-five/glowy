# Research: Умные заметки

## Решение 1: Аддитивная модель заметок и связей

- **Decision**: Добавить `Note` и явную уникальную связь `NoteTaskLink` с
  cascade при удалении пользователя/заметки/задачи.
- **Rationale**: Связь many-to-many нужна для переходов в обе стороны, явная
  модель оставляет место для времени создания и будущих sync-метаданных.
- **Alternatives considered**: Один `taskId` в заметке ограничивает связи;
  массив идентификаторов не обеспечивает ссылочную целостность.

## Решение 2: Надёжное сохранение редактора

- **Decision**: Создавать заметку после первого непустого содержимого, затем
  сохранять явной кнопкой и при переходе/потере фокуса; UI хранит номер локальной
  ревизии и принимает ответ только для последней отправленной версии.
- **Rationale**: Пользователь видит точный статус и запоздавший ответ не
  перезаписывает более новый текст. Явное сохранение остаётся доступным при
  сетевой ошибке.
- **Alternatives considered**: Только autosave скрывает момент ошибки; сохранение
  на каждый символ создаёт гонки и лишнюю нагрузку.

## Решение 3: Серверный поиск и архив

- **Decision**: `GET /api/notes?query=&archived=` фильтрует по владельцу,
  состоянию архива и регистронезависимому совпадению заголовка/текста; запрос
  debounce на клиенте.
- **Rationale**: Ownership остаётся на backend, контракт готов к росту данных,
  а одна страница до 500 заметок достаточна для v2.7.0.
- **Alternatives considered**: Клиентский поиск требует заранее скачать все
  приватные тексты и хуже масштабируется; полнотекстовый индекс избыточен для MVP.

## Решение 4: Атомарное подтверждение AI-черновика

- **Decision**: AI endpoint возвращает нормализованный task draft без записи.
  Отдельный confirm endpoint создаёт задачу и связь в одной транзакции.
- **Rationale**: Отмена ничего не мутирует, повторный UI submit можно блокировать,
  а частичная задача без связи не остаётся при ошибке.
- **Alternatives considered**: Последовательные frontend-запросы create/link
  допускают частичный успех; автоматическое сохранение нарушает конституцию.

## Решение 5: Переиспользование AI и лимитов

- **Decision**: Новый небольшой prompt/parser service вызывает существующий
  `generateContentWithAiProvider`, предварительно проверяет лимит и списывает
  успешный провайдерский запрос по текущему authenticated flow.
- **Rationale**: Ключи остаются на backend, сохраняются аналитика стоимости,
  тарифные правила и единые graceful errors.
- **Alternatives considered**: Frontend AI вызов раскрывает секреты; отдельный
  proxy/лимитер создаёт запрещённую параллельную архитектуру.

## Решение 6: Offline scope

- **Decision**: Заметки не подключаются к task offline snapshot/queue в v2.7.0.
  Модель получает стабильный id и `updatedAt`, а UI честно сообщает о сетевой
  ошибке сохранения.
- **Rationale**: Это прямо ограничено roadmap и предотвращает смешение разных
  sync-контрактов.
- **Alternatives considered**: Расширение очереди v2.6 требует отдельного
  конфликторазрешения и существенно увеличивает риск релиза.
