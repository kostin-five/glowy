# Архитектура Glowy

## Границы системы

```text
React + Vite frontend
  -> HTTPS API
Express backend
  -> Prisma (один общий клиент) -> PostgreSQL
  -> AI service/provider -> DeepSeek API
                         -> GigaChat API (temporary-failure fallback)
  -> YooKassa API
YooKassa webhook -> Express backend -> PostgreSQL
Telegram webhook -> Express backend -> PostgreSQL queue -> Telegram worker -> Bot API
Telegram Mini App -> existing React routes -> existing Express API
```

### Frontend

`src/pages/` собирает маршруты и экраны. `src/api/` отвечает за HTTP-вызовы, а `src/store/` -- за
клиентское Zustand-состояние. Общие UI-компоненты находятся в `src/components/`, чистые helpers --
в `src/utils/`. Браузер не получает ключи AI, YooKassa или базы данных.

На экранах уже desktop breakpoint `lg` `BottomNav` показывает пять основных действий:
«Главная», «Задачи», центральный Glowy AI, «Мой прогресс» и «Ещё». Центральная SVG-кнопка
открывает доступный модальный bottom sheet с быстрой «Разгрузкой мыслей»; «Ещё» открывает ссылки
на существующие Аналитику и Настройки. Оба листа используют Headless UI для focus trap, Escape и
возврата фокуса и закрываются при смене маршрута.

### Backend и база

Express принимает запросы, применяет CORS, CSRF-проверку, `requestId` и маршруты. Prisma
импортируется только из `backend/lib/prisma.js`; это единственный клиент Prisma и пул соединений
для процесса. PostgreSQL хранит пользователей, задачи, подзадачи, платежи и состояние тарифов.

### AI и Разгрузка мыслей

Маршруты в `backend/routes/ai.routes.js` передают работу в `backend/services/ai/`. Там находятся
provider, анализ Разгрузки мыслей, fallback и лимиты. Backend напрямую вызывает DeepSeek. Только
при timeout, сетевой ошибке, HTTP 429 или HTTP 5xx один раз вызывается GigaChat; успешный запрос не
отправляется двум провайдерам. Короткоживущий OAuth-токен GigaChat кешируется в памяти процесса.
Ключи обоих провайдеров остаются только на сервере;
текст задач и контекст не передаются в браузерные аналитические события.

AI endpoint возвращает разговорный ответ и необязательные несохранённые черновики задач. Он не
создаёт и не изменяет задачи. Пользователь может отредактировать или отклонить черновик; только
явное подтверждение вызывает существующий Task API, который остаётся единственной точкой записи
для этого сценария. Событие подтверждения не содержит текст сообщения, задачи или подзадач.

Быстрый лист и защищённая страница `/ai` используют один `MindHubChat`, `AiApi` и frontend store
текущего browser-local разговора. Store синхронизирует сообщения и ожидающие черновики между
поверхностями, но не является новым хранилищем задач: pending draft попадает в Task API только
после явного подтверждения. Серверная история и синхронизация диалогов между устройствами пока не
реализованы.

### Оплата

Frontend запускает существующий checkout Focus через backend. Backend создаёт платёж в YooKassa,
сохраняет его и возвращает URL подтверждения. После оплаты YooKassa вызывает webhook; backend
повторно проверяет платёж у провайдера, сверяет допустимые значения и обновляет тариф пользователя.
Клиентская страница результата не является источником истины.

Пожизненный доступ хранится и возвращается под единым тарифом `forever`. На публичной странице
тарифов Forever имеет только неактивную кнопку «Скоро». Pricing не содержит бесплатной
активации, а совместимый backend endpoint возвращает `410 PLAN_UNAVAILABLE` до обращения к БД.
Существующие и вручную назначенные права продолжают проверяться на backend; новое платное
оформление остаётся за выключенным feature flag.

### Локальный аналитический отчёт

Сформированный глубокий разбор сохраняется только в browser `localStorage` по ключу, включающему
ID пользователя, тип периода и точные даты начала/конца. При смене аккаунта или периода чужой
отчёт не показывается. Frontend отображает ограниченный набор Markdown (заголовки, списки и
жирный текст) без HTML. Удаление явное; новый AI-разбор требует подтверждения и заменяет старый
только после успешного ответа. Это не серверная история и не синхронизация между устройствами.

### Telegram Mini App и бот-пульт

Маршрут `/telegram` — контролируемый bootstrap над существующим React-приложением. Он проверяет
наличие Telegram bridge, передаёт raw `initData` только в Telegram auth endpoint и после backend-
проверки открывает существующие protected routes: главную, задачи, заметки, Glowy AI, прогресс,
аналитику и настройки. Отдельного Telegram frontend, профиля или хранилища данных нет. Bridge
адаптирует theme params, viewport, safe areas, native BackButton и внешние HTTPS-переходы.

Backend принимает подписанный запуск не позднее пяти минут после `auth_date`. Несвязанный
пользователь регистрирует обычный Glowy-аккаунт или входит в существующий прямо внутри Mini App;
одна `TelegramConnection` создаётся транзакционно. Telegram-bound HttpOnly session живёт не более
24 часов и на каждом защищённом запросе сверяется с текущей связью. Unlink удаляет связь и сразу
делает старую сессию недействительной, не удаляя User, задачи или другие данные. Старый
десятиминутный одноразовый link-code остаётся совместимым дополнительным путём из web-настроек.

Mini App использует те же визуальные `LoginPage` и `RegisterPage`, что и web, но при наличии
проверяемого Telegram `initData` отправляет credentials в Telegram channel endpoints. Обычный
logout не удаляет `TelegramConnection`: он завершает web-сессию и сохраняет только локальный
нечувствительный признак запрета автовосстановления. После следующего успешного ручного входа
признак снимается. Это отличается от явного Unlink в настройках.

Webhook `/api/telegram/webhook` является единственным исключением browser-CSRF для Telegram,
проверяет отдельный `X-Telegram-Bot-Api-Secret-Token`, идемпотентно сохраняет update и сразу
отвечает. Фоновый worker использует эту же PostgreSQL через `backend/lib/prisma.js`; отдельного
Redis, пула или базы нет. Payload очищается после обработки, а логи не содержат сообщения,
callback data, Telegram identifiers, token или коды.

Бот открывает все основные разделы и даёт ограниченный быстрый пульт: `/today`, `/tasks`,
`/energy`, `/progress`, подтверждаемые `/add` и `/done`, а также `/ai` через существующий provider
и общий AI-limit. Общий completion-service сохраняет правила владельца и одноразового XP для HTTP
и Telegram. Выбранный `User.aiTone` остаётся совместимым идентификатором режима поведения:
backend выдаёт обычный, нулевой или отрицательный XP outcome с нижней границей 0, а offline после
синхронизации принимает серверный прогресс. Повторный callback не создаёт дубль. В v2.8.0 voice не скачивается, не сохраняется и
не отправляется платному STT: бот явно предлагает текстовый ввод или Mini App.

Progress API аддитивно возвращает ограниченный календарный срез выбранного месяца. Сетка и rescue
строятся только по данным текущего пользователя; rescue разрешён только для вчерашнего разрыва,
если позавчера уже входило в серию. Новая таблица или migration для этого не нужны.

### Наблюдаемость и тесты

Каждому backend-запросу назначается серверный `X-Request-Id`. Ошибки пишутся структурированно без
тела запроса, cookies, токенов, email, содержимого задач или AI-сообщений. CI запускает typecheck,
lint, unit tests, build, браузерные smoke-тесты и изолированные backend HTTP-тесты. Тесты, которым
нужны данные Prisma, должны появиться только вместе с отдельной test DB.
