## Purpose

Определяет переиспользуемую семантическую визуальную основу Glowy, чтобы следующие UI-изменения
сохраняли спокойный характер продукта, доступность и проверяемую визуальную целостность.

## ADDED Requirements

### Requirement: Семантический словарь визуальных ролей

Система дизайна SHALL предоставлять документированный и доступный frontend-набор токенов для
canvas/background, surface, text, border, primary, accent, status, typography, spacing, radii,
elevation/glow, focus и motion. Каждый токен MUST описывать семантическую роль, а не название
конкретного оттенка или компонента; новые shared UI-поверхности MUST выбирать токены по роли.

#### Scenario: Новая shared-поверхность выбирает фон и текст
- **WHEN** разработчик добавляет поверхность в следующий UI change
- **THEN** он выбирает документированные surface и text роли вместо локального набора palette-значений

#### Scenario: Визуальное значение уточняется
- **WHEN** требуется поменять значение роли для темы
- **THEN** изменение выполняется в token layer без переименования семантической роли в потребителях

### Requirement: Сохраняемая тема и характер Glowy

Token layer SHALL поддерживать существующие light, dark и system-настройки темы. Значения dark
темы MUST сохранять тёмную атмосферу Glowy, читаемость фирменной сферы и русского интерфейса; token
foundation MUST NOT менять логотипы, пользовательские тексты или навигационные сценарии.

#### Scenario: Пользователь меняет тему
- **WHEN** пользователь выбирает light, dark или system в существующих настройках
- **THEN** semantic token values соответствуют активной теме, а настройка продолжает применяться без
  изменения данных аккаунта

#### Scenario: Несвязанный экран ещё не мигрирован
- **WHEN** пользователь открывает существующий экран, не выбранный для foundation showcase
- **THEN** его пользовательское поведение и структура остаются прежними

### Requirement: Базовые критерии доступного взаимодействия

Документированные token pairings MUST обеспечивать контраст не ниже 4.5:1 для обычного текста и
3:1 для крупных текстов, интерактивных границ и focus-индикаторов там, где это применимо. Shared
interactive foundation states SHALL иметь видимый keyboard focus, соблюдать `prefers-reduced-motion`
для необязательной анимации и поддерживать минимальный target 44 × 44 CSS px для touch-управления.

#### Scenario: Пользователь перемещается по foundation showcase с клавиатуры
- **WHEN** фокус переходит на интерактивный элемент через клавишу Tab
- **THEN** активный элемент имеет отчётливо видимый focus-индикатор, отличный от состояния покоя

#### Scenario: Пользователь включает reduced motion
- **WHEN** браузер сообщает `prefers-reduced-motion: reduce`
- **THEN** необязательная foundation-анимация не проигрывается

### Requirement: Локальная проверка визуальной основы

Репозиторий SHALL содержать не включённую в пользовательскую навигацию foundation showcase и
локальные проверяемые visual baseline для desktop и mobile viewport в light и dark темах. Проверка
MUST выполняться средствами репозитория и MUST NOT требовать облачный visual-regression service или
production-доступ.

#### Scenario: Меняется token value
- **WHEN** pull request изменяет semantic token или foundation showcase
- **THEN** локальная visual-проверка выявляет непреднамеренное расхождение с сохранённой baseline
  до интеграции либо baseline обновляется как осознанная часть review

#### Scenario: Разработчик проверяет foundation локально
- **WHEN** он запускает документированную проверку в чистом локальном окружении
- **THEN** она не требует backend, пользовательских данных, секретов или внешнего visual-сервиса

### Requirement: Постепенное принятие основы

Введение token layer MUST быть обратно совместимым с действующими Tailwind-стилями и Headless UI
компонентами. Массовая замена экранов, подключение Storybook или замена primitive layer SHALL NOT
входить в foundation change; каждый следующий экран или primitive должен переходить отдельным
проверяемым change.

#### Scenario: Foundation change интегрируется
- **WHEN** token layer готов к использованию
- **THEN** существующие product routes сохраняют свои API, данные и пользовательские сценарии, а
  миграция UI остаётся явно ограниченной последующими changes
