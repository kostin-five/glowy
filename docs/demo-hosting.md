# Демонстрационное размещение

## Локальный гостевой доступ

Кнопка «Открыть демо без регистрации» открывает задачи и подзадачи, заметки
(поиск, архив, восстановление, удаление и связи с задачами), привычки и их отметки,
XP/уровень, серию, календарь, спасательные круги и достижения, не-AI аналитику
недели/месяца, аватар и обычные настройки. Кнопка «Настроить план» и её уведомление
удалены; блоки «Сегодня», энергии и следующего шага сохранены.

Все гостевые AI-вызовы заблокированы до сети: чат, голосовой ввод в чат, AI-подзадачи,
черновик задачи из заметки и AI-отчёт. Показывается «AI недоступен в демо-режиме».
Регистрация, платежи, Telegram linking и облачная синхронизация остаются закрыты;
демо не получает серверный тариф или права аккаунта.

Заметки, привычки, отметки, награды, спасательные круги и аватар хранятся в
версионированном IndexedDB `glowy-demo`; задачи/XP — в отдельном гостевом localStorage.
Обычные настройки используют существующее браузерное хранилище. Перезагрузка сохраняет
данные; переход в аккаунт не загружает их на сервер. Это не резервная копия: очистка
данных сайта, другой браузер/устройство или приватный режим могут их удалить.
При запрете/повреждении хранилища операции сообщают об ошибке, не имитируют сохранение.

Изменения сначала проверяются локально. Для публикации на `glowy-ai.ru` требуются
отдельное разрешение на push/deploy и новая Production-сборка; Preview на
`dev.glowy-ai.ru` не заменяет Production.

Timeweb недоступен, подтверждённого backup базы нет. Создаётся **новая пустая** база
без seed и тестовых пользовательских данных; это не восстановление старого production. Подтверждение
«пользователей нет» не заменяет резервную копию Git перед очисткой истории.

## Предлагаемая схема

- Vercel: статический frontend и same-origin `/api` rewrite к backend.
- Render: один бесплатный Node/Express web service; существующие сервисы делят лимит workspace.
- Neon: PostgreSQL, TLS с проверкой сертификата; secrets только в настройках backend.

Render выбран владельцем; существующий dev-сервис можно переиспользовать, новый не требуется.
Владелец переключил ветку существующего сервиса на master и выключил автодеплой.
Это не означает, что новые исправления уже развернуты. Условия free tier и доступность аккаунта
нужно проверить перед переносом. Workspace получает 750 free instance hours в месяц
на все работающие free web services вместе, спящие не расходуют часы. Через 15 минут
без входящего трафика сервис засыпает; пробуждение может занять около минуты.
Не использовать artificial keep-alive. Free runtime засыпает, AI-провайдер оплачивается
отдельно. Фоновый Telegram worker не гарантирует доставку во время сна; оставлять
`TELEGRAM_WORKER_ENABLED=false` до отдельного решения по его размещению.

## Сборка

Frontend: root directory репозитория, install `npm ci`, build `npm run build`, output `dist`.
Backend: root directory репозитория; build:

```sh
npm ci
npm --prefix backend ci
npm run build:backend
```

Start: `npm --prefix backend run start:prod`. Сервис должен передавать `PORT`.
Health: `/api/health`. Не включать optional ai-proxy без необходимости.

На Render Root Directory оставить пустым: backend зависит от `packages/contracts`.
Не выполнять `npm ci` из папки contracts — отдельного lockfile там может не быть.
Blueprint в `render.yaml` — шаблон одного demo-сервиса, его применение не удаляет
существующие три сервиса. В шаблоне явно выбраны `master` и выключенный автодеплой.
Не применять Blueprint как новый сервис, если переиспользуется существующий dev:
другое имя в шаблоне может создать дополнительный сервис. Фактический остаток часов
нужно смотреть в dashboard.

## Переиспользование Render dev вместо нового сервиса

### Вариант: dev как ветка живого демо

Владелец предложил оставить `master` основной веткой для просмотра исходников,
а существующее Render/Vercel/Neon окружение связать с `dev`. Это допустимая
альтернатива схеме ниже, но ещё не изменение внешних настроек: сейчас Render
переключён владельцем на `master`, автодеплой выключен. Перед выбором `dev`
проверить обе ветки, окружение и целевую Neon базу; дождаться зелёного CI.

GitHub публикует весь репозиторий, а не только default branch. Очищенная история
должна охватывать все публикуемые ветки и теги. Обычный merge удалений этого не
обеспечивает. Смена Git-ветки сама по себе не меняет URL Render: `/api` rewrite
нужно обновлять только при смене фактического адреса backend. Vercel Production
Branch может быть `dev` независимо от default branch GitHub `master`.
Не подключать preview-сборки к общей базе автоматически; регистрация, checkout
и фоновый worker остаются выключены. Обе ветки синхронизировать только после
проверки актуального remote; переписывающий push требует отдельного разрешения.

Смена ветки не переносит данные и не объединяет Git-ветки. Настройки сервиса,
подключённая база и переменные окружения не становятся production-ready автоматически.

1. Зафиксировать имя/ID выбранного сервиса, текущую ветку и последний рабочий commit.
   Убедиться, что его dev URL не нужен другим приложениям. Не публиковать значения secrets.
2. В Settings выбрать Auto-Deploy → Off до изменения ветки или окружения.
3. Подготовить и отдельно согласовать новую пустую demo-базу и миграции. Не подменять
   базу существующего сервиса без проверки её назначения и сохранности данных.
4. Отправить проверенные исправления через обычный review/merge в `master`; дождаться CI.
   Локальные правки в `codex/public-pet-project` ещё не находятся в удалённом `master`.
5. В Settings выбрать Branch → `master`, пустой Root Directory, build/start/health из
   раздела «Сборка». В Environment настроить backend secrets и выключенные платежи/worker.
   Не добавлять миграцию в каждый start или build: её целевой адрес проверяется отдельно.
6. После отдельного разрешения выполнить Manual Deploy для проверенного commit.
   Проверить не только health, но также вход, logout/replay, задачи и доступ к базе.
7. Направить Vercel `/api` rewrite на фактический URL этого же сервиса. Если URL не
   изменился, переписывать его без необходимости не требуется. Проверить web и Mini App.
8. После smoke можно выбрать Auto-Deploy → After CI Checks Pass. Остальные сервисы
   останавливать только по согласованным ID, если они не нужны другим проектам.

До первого переключения сохранить прошлые настройки приватно. Rollback возвращает
предыдущий рабочий artifact и настройки сервиса; он не откатывает миграции или данные.
Не возвращаться автоматически к небезопасной версии только ради зелёного health.
Для портфолио отдельный постоянно работающий dev backend не обязателен: `dev` остаётся
Git-веткой, локальные проверки и Vercel preview сохраняются.

Порядок и параметры сверены с [Render Deploys](https://render.com/docs/deploys) и
[Blueprint Reference](https://render.com/docs/blueprint-spec) 2026-10-06.

Neon рекомендуется как минимальная PostgreSQL без смены auth/Prisma. Один существующий
проект не является исчерпанием free-plan лимита проектов. Supabase тоже совместим:
использовать его только как PostgreSQL, не добавлять Supabase Auth параллельно.
Free Supabase ограничен двумя активными проектами, 500 MB базы на проект и может
приостанавливаться после недели низкой активности. Для Render без IPv6 использовать
Supabase Session pooler, а не transaction-mode URL; сертификат проверять с CA провайдера.
Новая база остаётся отдельным шагом владельца, провайдер не переключён автоматически.

Источники тарифных ограничений (проверены 2026-10-05):
[Render Free](https://render.com/docs/free),
[Neon Free](https://neon.com/blog/neon-free-plan-1-gb-per-project),
[Supabase Billing](https://supabase.com/docs/guides/platform/billing-on-supabase),
[Supabase Pausing](https://supabase.com/docs/guides/platform/free-project-pausing).

## Новая база — только после выбора владельца

Создать отдельную demo-базу. В настройках backend установить `DATABASE_URL`, новый
случайный `JWT_SECRET` (минимум 32 символа), `NODE_ENV=production`, точный HTTPS
`CORS_ORIGINS`, `PAYMENTS_ENABLED=false`, `REGISTRATION_ENABLED=false`. На frontend
оставить `VITE_REGISTRATION_ENABLED=false`. Не копировать старые секреты или личные данные.
Для удалённой базы не использовать `DATABASE_TLS_MODE=local` и не отключать TLS.
`TRUST_PROXY_HOPS` выбрать по фактической схеме proxy, а не вслепую.

После явного согласования применить `npm --prefix backend run migrate:deploy`
**только к новой целевой базе**. Включена аддитивная таблица отозванных сессий; без неё
авторизация новой версии работать не должна.

Seed удалён по решению владельца. Не создавать тестовые аккаунты, задачи и платежи
в PostgreSQL, в том числе во время smoke. Для посетителей есть клиентский гостевой
режим без серверного аккаунта. Предыдущая локальная проверка миграций на временной
PostgreSQL не подтверждает готовность внешней базы Neon или Render deployment.
Регистрация закрыта на сервере, включая Mini App; вход существующих аккаунтов сохранён.
Яндекс Метрика и аналитический баннер удалены; технические cookies авторизации сохранены.

Если позже обнаружится backup старой базы: не импортировать его автоматически.
Сначала согласовать состав данных, создать отдельную изолированную базу для review,
проверить совместимость миграций и исключить реальные аккаунты из публичного demo.
Подтверждение владельца требуется отдельно; этот сценарий сейчас не выполнялся.

В `vercel.json` заменить destination `/api` на выбранный backend URL до deployment.
Не передавать JWT, DB, Telegram или AI credentials через переменные `VITE_*`.

## Gate перед переключением

На внешнем hosting проверить health, отказ регистрации/checkout, гостевой режим,
CSP и cold start без записи тестовых данных в базу. Auth/logout, ownership, AI quota
и Telegram проверяются database-free тестами; непроверенные живые account flows
явно отметить до релиза. Яндекс Метрика не должна загружаться даже при старом согласии.
Не выключать старый Render dev-сервис до успешного smoke новой схемы и отдельного
подтверждения удаления. DNS и webhook не переключать автоматически.
