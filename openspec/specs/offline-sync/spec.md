# Offline Task Sync Specification

## Purpose

Определяет устойчивую работу задач без сети: account-scoped cache, optimistic mutations,
последовательную синхронизацию и понятное состояние ошибок без потери пользовательских действий.

## Requirements

### Requirement: Account-scoped offline snapshot

Glowy SHALL сохранять snapshot задач авторизованного пользователя в IndexedDB с owner key и MUST
NOT показывать snapshot одного аккаунта другому. Сохранённая auth-информация может открыть
локальный интерфейс без сетевой проверки, но не создаёт новую серверную сессию.

#### Scenario: Открытие без сети
- **WHEN** ранее вошедший пользователь открывает приложение offline
- **THEN** Glowy восстанавливает только его cached tasks и показывает offline-состояние

### Requirement: Optimistic task mutations

Создание, изменение, завершение и удаление задач и подзадач SHALL немедленно отражаться локально и
записываться в устойчивую очередь до попытки синхронизации.

#### Scenario: Создание задачи offline
- **WHEN** авторизованный пользователь создаёт задачу без сети
- **THEN** интерфейс показывает сущность с временным локальным id и сохраняет create operation

### Requirement: Компактизация очереди

Glowy SHALL объединять последовательные updates одной сущности и удалять взаимно уничтожающиеся
операции create/delete для ещё не синхронизированных задач и подзадач.

#### Scenario: Создание и удаление до reconnect
- **WHEN** локальная задача создаётся и удаляется до отправки на backend
- **THEN** sync не отправляет ни create, ни зависимые операции этой задачи

### Requirement: Последовательная синхронизация

При восстановлении сети Glowy SHALL применять операции текущего owner в порядке очереди, заменять
локальные ids серверными, сохранять completion progress и после пустой очереди обновлять snapshot
с backend без перезаписи более новых локальных mutations.

#### Scenario: Reconnect после нескольких изменений
- **WHEN** сеть возвращается и очередь содержит связанные task/subtask operations
- **THEN** Glowy выполняет их последовательно, remap-ит ids и получает итоговое серверное состояние

### Requirement: Состояния и повтор

Glowy SHALL различать offline, syncing, idle и attention, сохранять pending operations при сетевой,
`429` или `5xx` ошибке и позволять повторить синхронизацию без скрытой потери очереди.

#### Scenario: Временная ошибка backend
- **WHEN** sync получает сетевую ошибку, `429` или `5xx`
- **THEN** операции остаются в IndexedDB, а пользователь видит, что изменения сохранены на устройстве

### Requirement: Межвкладочная согласованность

Glowy SHALL координировать sync одного аккаунта между вкладками через browser lock при наличии и
сообщать обновления snapshot/state через BroadcastChannel.

#### Scenario: Две вкладки синхронизируются одновременно
- **WHEN** browser lock доступен и обе вкладки запускают sync одного owner
- **THEN** очередь обрабатывает только получившая lock вкладка, а вторая получает опубликованное состояние

### Requirement: Ограниченная область offline

Полный offline mutation contract SHALL распространяться только на задачи и подзадачи. AI, заметки,
аналитика, платежи, Telegram и серверные настройки MUST показывать сетевое ограничение и не
имитировать успешную серверную запись.

#### Scenario: AI-запрос offline
- **WHEN** пользователь запускает AI-сценарий без сети
- **THEN** приложение не создаёт ложный AI-результат и объясняет необходимость соединения
