# Feature Specification: Быстрое создание и режимы полей задачи

**Feature Branch**: `codex/task-capture-fields`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "Сделать Glowy заметно удобнее: дать возможность быстро записать задачу и добавить короткий, средний и полный набор полей, чтобы пользователь мог скрывать ненужные энергию и приоритет. Сохранить текущий стиль, mobile-first UX, совместимость старых задач и правило явного подтверждения AI-действий."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Быстро записать задачу (Priority: P1)

Пользователь открывает создание задачи, сразу вводит понятное название и сохраняет задачу, не проходя через необязательные параметры.

**Why this priority**: Быстрая фиксация мысли — самый частый и ценный путь. Обязательное заполнение второстепенных полей мешает использовать Glowy как спокойный ежедневный инструмент.

**Independent Test**: Открыть короткую форму на mobile и desktop, ввести только название, создать задачу и убедиться, что она сразу появилась в текущем списке и сохранилась после повторного открытия приложения.

**Acceptance Scenarios**:

1. **Given** пользователь находится на экране задач, **When** он запускает быстрое создание, вводит только название и подтверждает, **Then** задача создаётся с безопасными значениями по умолчанию и появляется в списке.
2. **Given** форма открыта без названия, **When** пользователь пытается сохранить её, **Then** создание не выполняется и форма понятно указывает единственное обязательное поле.
3. **Given** пользователь закрыл форму или нажал «Отмена», **When** он возвращается к задачам, **Then** новая задача не создаётся и существующие задачи не меняются.
4. **Given** устройство временно находится без сети после успешного онлайн-сеанса, **When** пользователь создаёт короткую задачу, **Then** применяется существующее безопасное offline-поведение и пользователь видит фактическое состояние сохранения или синхронизации.

---

### User Story 2 - Выбрать подходящую подробность формы (Priority: P1)

Пользователь выбирает короткий, средний или полный режим формы в зависимости от того, хочет ли он только записать действие или подробно его спланировать.

**Why this priority**: Один перегруженный набор полей одинаково неудобен и для быстрого ввода, и для подробного планирования. Progressive disclosure сохраняет возможности Glowy без визуального шума.

**Independent Test**: Последовательно открыть каждый режим и подтвердить, что виден только предусмотренный набор полей, введённые значения не теряются при переключении, а созданная задача содержит выбранные данные.

**Acceptance Scenarios**:

1. **Given** выбрана короткая форма, **When** пользователь открывает создание, **Then** основное внимание получает название, а дополнительные поля доступны через одно явное действие.
2. **Given** выбрана средняя форма, **When** пользователь открывает создание, **Then** кроме названия он видит основные параметры планирования без полного набора деталей.
3. **Given** выбрана полная форма, **When** пользователь открывает создание или редактирование, **Then** доступны все поддерживаемые поля и подзадачи без изменения их прежнего смысла.
4. **Given** пользователь заполнил поле и переключил режим, **When** поле стало скрытым, **Then** введённое значение сохраняется в текущем черновике и не сбрасывается без явного действия.

---

### User Story 3 - Скрыть энергию и приоритет (Priority: P2)

Пользователь, которому не нужны энергия или приоритет, отключает их показ в формах, сохраняя возможность вернуть поля позже.

**Why this priority**: Эти поля являются важной частью адаптивного планирования Glowy, но не должны становиться обязательным барьером для людей с более простым способом ведения задач.

**Independent Test**: Отключить оба поля, создать и отредактировать задачу, затем вернуть их и убедиться, что задачи остаются совместимыми, а интерфейс не требует скрытых значений.

**Acceptance Scenarios**:

1. **Given** пользователь отключил показ энергии, **When** он открывает форму задачи, **Then** поле энергии не занимает место, а задача всё равно может быть создана.
2. **Given** пользователь отключил показ приоритета, **When** он открывает форму задачи, **Then** поле приоритета скрыто и не требуется для сохранения.
3. **Given** оба поля скрыты, **When** пользователь открывает дополнительные параметры или настройки формы, **Then** он может вернуть каждое поле независимо.
4. **Given** старая задача уже содержит энергию и приоритет, **When** пользователь редактирует её со скрытыми полями, **Then** существующие значения не удаляются только из-за скрытия интерфейса.

---

### User Story 4 - Использовать одну понятную форму на разных экранах (Priority: P2)

Пользователь получает одинаковые правила создания и редактирования задачи на desktop и mobile, включая понятное закрытие, подтверждение и восстановление после ошибки.

**Why this priority**: Разные формы или разные значения по умолчанию создают ошибки и недоверие, особенно когда один аккаунт используется на сайте и в Telegram Mini App.

**Independent Test**: Создать и отредактировать задачи в поддерживаемых ширинах mobile и на desktop, проверить клавиатуру, прокрутку, закрытие, ошибки и одинаковый итоговый набор данных.

**Acceptance Scenarios**:

1. **Given** ширина экрана от 320 до 430 px, **When** пользователь открывает форму, **Then** все обязательные элементы доступны без горизонтальной прокрутки и не перекрываются нижней навигацией.
2. **Given** desktop-экран, **When** пользователь открывает форму, **Then** фокус попадает в название, фон остаётся контекстом, а закрытие доступно мышью и клавиатурой.
3. **Given** сохранение завершилось ошибкой, **When** пользователь остаётся в форме, **Then** введённые значения сохраняются и можно безопасно повторить действие.
4. **Given** предложение создано AI, **When** пользователь его просматривает, **Then** оно остаётся черновиком и не создаёт или не меняет задачу до отдельного явного подтверждения.

### Edge Cases

- Название состоит только из пробелов, слишком длинное или содержит переносы строк.
- Пользователь быстро нажимает кнопку создания несколько раз или повторяет действие после медленного ответа.
- Форма закрывается клавишей Escape, кнопкой закрытия, системной кнопкой «Назад» или касанием фона.
- Пользователь переключает режим после заполнения скрываемых полей.
- Настройка полей отсутствует у существующего пользователя или содержит устаревшее значение.
- Старая задача содержит неизвестное или пустое значение энергии/приоритета.
- Сохранение начинается online, но соединение пропадает до получения результата.
- Offline-очередь уже содержит несинхронизированное создание или изменение той же задачи.
- Экранная клавиатура уменьшает доступную высоту mobile-формы.
- Пользователь открывает вторую форму, пока первая ещё содержит несохранённый черновик.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Пользователь MUST иметь возможность создать задачу, указав только непустое название.
- **FR-002**: Система MUST предоставлять три режима формы: «Коротко», «Средне» и «Полно».
- **FR-003**: Короткий режим MUST показывать название как единственное обязательное поле и один понятный способ раскрыть дополнительные параметры.
- **FR-004**: Средний режим MUST показывать название, дату, длительность и проект, а также только те поля энергии и приоритета, которые пользователь не скрыл.
- **FR-005**: Полный режим MUST сохранять доступ ко всем полям и подзадачам, которые поддерживает текущая форма задачи.
- **FR-006**: Переключение режима MUST NOT удалять уже введённые значения из текущего черновика.
- **FR-007**: Пользователь MUST иметь возможность независимо скрыть и вернуть поля энергии и приоритета.
- **FR-008**: Скрытие поля MUST изменять только представление формы и MUST NOT удалять соответствующее значение у существующей задачи.
- **FR-009**: Новая задача без явно выбранных энергии и приоритета MUST получать совместимые безопасные значения, чтобы существующие списки, Focus, XP, аналитика, offline и Telegram продолжили работать.
- **FR-010**: Выбранный режим формы и видимость энергии/приоритета MUST сохраняться отдельно для текущего аккаунта на устройстве и не показываться другому аккаунту.
- **FR-011**: При отсутствии сохранённых настроек MUST использоваться средний режим с видимыми энергией и приоритетом, соответствующий прежнему поведению.
- **FR-012**: Создание и редактирование MUST использовать одинаковые названия режимов, правила видимости и интерпретацию полей.
- **FR-013**: Форма MUST предотвращать повторное создание одной задачи из-за двойного нажатия во время сохранения.
- **FR-014**: При ошибке сохранения форма MUST сохранить черновик и показать понятную возможность повторить действие или отменить его.
- **FR-015**: Отмена или закрытие формы MUST NOT создавать задачу и MUST NOT изменять существующие данные.
- **FR-016**: Mobile-форма MUST работать без горизонтальной прокрутки на поддерживаемых ширинах 320, 360, 390 и 430 px.
- **FR-017**: Открытая mobile-форма MUST сохранять доступ к основным действиям при появлении экранной клавиатуры и не конфликтовать с нижней навигацией.
- **FR-018**: Desktop-форма MUST поддерживать предсказуемый фокус, закрытие клавишей Escape и возврат фокуса к элементу, который её открыл.
- **FR-019**: Функция MUST переиспользовать текущие правила создания, редактирования, авторизации, offline-синхронизации и серверной проверки задач.
- **FR-020**: AI MUST показывать любое предложение задачи или подзадач как редактируемый черновик и MUST NOT сохранять его без явного подтверждения пользователя.
- **FR-021**: Этот slice MUST NOT добавлять новый AI-запрос для разбиения задачи; отдельный AI-flow остаётся последующим независимым блоком.
- **FR-022**: Функция MUST сохранять русский пользовательский текст и MUST NOT изменять landing page.
- **FR-023**: Функция MUST NOT требовать изменения production-схемы, внешних сервисов, тарифов или AI-лимитов.
- **FR-024**: Возврат к прежней единой форме MUST быть возможен без изменения или восстановления пользовательских задач.

### Key Entities

- **Черновик задачи**: Несохранённый набор введённых значений, режим отображения которого может меняться без потери данных.
- **Режим формы**: Предпочтение «Коротко», «Средне» или «Полно», определяющее первоначально видимый набор полей.
- **Настройка видимости поля**: Отдельный выбор пользователя для энергии и приоритета, влияющий на форму, но не удаляющий данные задачи.
- **Задача**: Существующая пользовательская сущность с текущими правилами доступа, сохранения, offline-синхронизации, аналитики и Telegram-совместимости.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может создать задачу только с названием не более чем за 15 секунд и не более чем за три действия после открытия формы.
- **SC-002**: На ширинах 320, 360, 390 и 430 px 100% обязательных полей и действий доступны без горизонтальной прокрутки.
- **SC-003**: В автоматических сценариях 100% переключений между тремя режимами сохраняют введённые значения текущего черновика.
- **SC-004**: В автоматических сценариях 100% старых задач сохраняют прежние энергию и приоритет после редактирования со скрытыми полями.
- **SC-005**: Двойное подтверждение во время одного сохранения создаёт не более одной задачи.
- **SC-006**: Ошибка сохранения не очищает название и заполненные параметры в 100% проверяемых сценариев.
- **SC-007**: Созданные задачи одинаково доступны после повторного открытия, offline/reconnect и входа в тот же аккаунт через поддерживаемый клиент.
- **SC-008**: Ни один сценарий AI-предложения в области изменения не создаёт или не меняет пользовательские данные до явного подтверждения.
- **SC-009**: Все существующие поддерживаемые task, offline, analytics и Telegram-проверки проходят без незапланированного изменения контрактов.

## Assumptions

- Первый slice охватывает существующие формы создания и редактирования задач и быстрый вход на экране задач; глобальный launcher с любой страницы оценивается отдельно после проверки этого сценария.
- «Коротко», «Средне» и «Полно» управляют видимостью, а не создают разные типы задач.
- Средний режим с видимыми энергией и приоритетом является безопасным значением по умолчанию для существующих пользователей.
- Предпочтения формы можно хранить в существующем локальном account-scoped слое настроек; серверная синхронизация предпочтений не входит в первый slice.
- Текущие значения по умолчанию задачи сохраняются ради совместимости Focus, XP, аналитики, offline и Telegram.
- Подробный AI-разбор задачи и генерация подзадач будут отдельным specification после завершения базовой формы.
- Production deploy, push, backup, schema migration и изменения внешней инфраструктуры не входят в работу.
