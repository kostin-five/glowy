# Research: Поведенческие режимы и честный прогресс

## Decision 1: Сохранить `aiTone`, изменить продуктовый смысл

**Decision**: Переиспользовать `calm`, `moderate`, `strict` и существующее профильное поле, но в UI и документации называть их режимами поведения.

**Rationale**: Старые пользователи, auth-store, API и база уже понимают эти значения. Смена схемы не добавляет пользовательской ценности и создаёт migration-риск.

**Alternatives considered**: Новое поле `behaviorMode` отвергнуто как дублирование; client-only настройка отвергнута, потому что XP и AI-policy должны проверяться на backend.

## Decision 2: Signed XP delta с нижней границей 0

**Decision**: Calm выдаёт обычную награду. Moderate возвращает delta 0 при другой активной просрочке. Strict возвращает отрицательную обычную награду, ограниченную доступным XP. Завершение самой overdue task не блокирует себя.

**Rationale**: Правило непосредственно следует продуктовой инструкции, остаётся объяснимым и применяется один раз через существующий `xpAwarded` guard. Clamp предотвращает некорректный отрицательный прогресс.

**Alternatives considered**: Ежедневный cron-штраф отвергнут как скрытая повторяемая санкция и новая инфраструктура; фиксированный штраф отвергнут как несвязанный со сложностью действия; отказ награждать саму overdue task отвергнут как демотивация закрывать долг.

## Decision 3: Один completion policy для HTTP и Telegram

**Decision**: Вынести вычисление исхода в shared task completion domain и использовать его из обоих путей. Offline продолжает отправлять HTTP mutation.

**Rationale**: Сейчас HTTP route и Telegram service отдельно начисляют XP. Новое поведение усиливает риск расхождения и повторного эффекта.

**Alternatives considered**: Дублировать if/else в routes отвергнуто; создавать новый endpoint только для XP отвергнуто как параллельный mutation flow.

## Decision 4: Строгий AI — дисциплина без abuse

**Decision**: Calm признаёт состояние и предлагает малый шаг; Moderate нейтрально фиксирует факт и предлагает решение; Strict называет невыполнение и требует выбрать действие или честно перепланировать. Все режимы запрещают оскорбления, унижение, угрозы, дискриминацию и оценку личности.

**Rationale**: Это создаёт ощутимую разницу и выполняет прямой запрос на требовательность, сохраняя безопасную продуктовую границу.

**Alternatives considered**: Только менять adjective в одном prompt отвергнуто как уже доказанно незаметное; разрешить унижающий copy отвергнуто как небезопасное и противоречащее контролю пользователя.

## Decision 5: Bounded calendar response

**Decision**: Progress response для одного выбранного месяца содержит полную 7-column grid и state каждого дня. Текущий response остаётся additive.

**Rationale**: Клиент получает готовую, тестируемую и user-scoped картину без передачи всей истории и без сложных расхождений вычислений между web и Telegram.

**Alternatives considered**: Отдавать всю историю dates отвергнуто как unbounded; строить календарь только из current streak days отвергнуто, потому что пропуски и прошлый месяц будут неверными.

## Decision 6: Rescue eligibility is exactly yesterday

**Decision**: Единственный кандидат — `today - 1`; обязательное условие — `today - 2` уже входит в streak set.

**Rationale**: Правило легко объяснить, проверить и невозможно использовать для ретроспективного исправления любой старой серии.

**Alternatives considered**: Искать последний одиночный разрыв отвергнуто как текущее неправильное поведение; разрешать rescue без предыдущего дня отвергнуто, потому что спасать нечего.

## Decision 7: Existing estimated minutes is the planned time

**Decision**: Показывать `estimatedMinutes` как duration chip и не добавлять время начала.

**Rationale**: В коде, API и базе уже есть необязательная плановая длительность, соответствующая roadmap. Пользователь уточнил красивое отображение, а не новый scheduling flow.

**Alternatives considered**: Новое поле clock time отвергнуто как scope будущего календаря v3.1 и schema migration.
