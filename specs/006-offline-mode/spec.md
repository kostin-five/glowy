# Feature Specification: Offline-режим задач

**Feature Branch**: `codex/v2.6.0-offline-mode`

**Created**: 2026-08-22

**Status**: Ready for planning

**Input**: User description: "Сделать версию 2.6.0 про offline-режим."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Открыть задачи без интернета (Priority: P1)

Авторизованный пользователь, который уже открывал Glowy на устройстве, может
повторно открыть приложение без сети и увидеть последний сохранённый список
задач и подзадач. Интерфейс явно сообщает, что данные показаны с устройства.

**Why this priority**: Без доступного списка задач offline-режим не даёт
пользователю основной ценности Glowy.

**Independent Test**: Открыть задачи онлайн, отключить сеть, перезагрузить
страницу и убедиться, что задачи доступны, а статус «Офлайн» виден.

**Acceptance Scenarios**:

1. **Given** пользователь вошёл и хотя бы один раз загрузил задачи, **When** он
   открывает приложение без сети, **Then** отображается последний локально
   сохранённый список задач и подзадач.
2. **Given** на устройстве ещё нет локальных данных, **When** пользователь
   впервые открывает защищённый экран без сети, **Then** приложение показывает
   понятное пустое состояние и не выдаёт данные другого аккаунта.
3. **Given** приложение открыто без сети, **When** пользователь переходит между
   Главной и Задачами, **Then** локальные данные остаются доступны без повторной
   сетевой ошибки на весь экран.

---

### User Story 2 - Изменить задачи офлайн (Priority: P1)

Пользователь может без сети создать, изменить, завершить и удалить задачу, а
также создать, изменить, завершить и удалить подзадачу. Результат появляется
сразу, сохраняется после перезагрузки и помечается как ожидающий синхронизации.

**Why this priority**: Пользователь должен не только читать план, но и продолжать
работу в метро, самолёте или при нестабильной связи.

**Independent Test**: Отключить сеть, выполнить каждое действие, перезагрузить
страницу и проверить сохранность результата и счётчика ожидающих действий.

**Acceptance Scenarios**:

1. **Given** приложение офлайн, **When** пользователь создаёт задачу, **Then**
   задача сразу появляется в списке и остаётся после перезагрузки.
2. **Given** приложение офлайн, **When** пользователь редактирует, завершает или
   удаляет существующую задачу, **Then** локальный список сразу отражает действие.
3. **Given** приложение офлайн, **When** пользователь меняет подзадачу, **Then**
   изменение сохраняется вместе с родительской задачей и переживает перезагрузку.
4. **Given** есть несинхронизированные действия, **When** пользователь закрывает
   и снова открывает Glowy, **Then** очередь не теряется и её размер остаётся
   видимым.

---

### User Story 3 - Автоматически синхронизировать изменения (Priority: P1)

После восстановления сети Glowy автоматически отправляет накопленные изменения
по порядку, заменяет временные идентификаторы серверными и показывает итоговый
статус. Ошибка одного действия не удаляет оставшуюся очередь.

**Why this priority**: Локальные изменения должны надёжно вернуться в основной
аккаунт, иначе offline-режим создаёт риск потери плана.

**Independent Test**: Создать и изменить задачу офлайн, включить сеть, дождаться
статуса завершения и проверить результат после чистой загрузки с сервера.

**Acceptance Scenarios**:

1. **Given** в очереди есть изменения, **When** сеть возвращается, **Then**
   синхронизация запускается автоматически и действия отправляются по порядку.
2. **Given** офлайн создана задача с подзадачами, **When** синхронизация успешна,
   **Then** временные идентификаторы заменяются серверными без дубликатов в UI.
3. **Given** сервер временно недоступен, **When** отправка не удалась, **Then**
   действие остаётся в очереди, а пользователь видит «Требуется внимание» и
   может повторить синхронизацию.
4. **Given** очередь полностью обработана, **When** пользователь обновляет
   страницу онлайн, **Then** серверный список соответствует последнему
   локальному состоянию.

---

### User Story 4 - Понимать ограничения offline-режима (Priority: P2)

Пользователь в любой момент понимает, есть ли сеть, сохранены ли изменения
только на устройстве и какие функции требуют подключения.

**Why this priority**: Честные статусы снижают тревогу и не создают ложного
ощущения, что AI или платёж работают без сети.

**Independent Test**: Переключать сеть и проверять статусы в приложении, а затем
попытаться вызвать сетевую функцию.

**Acceptance Scenarios**:

1. **Given** сеть отключена, **When** открыт защищённый экран, **Then** виден
   ненавязчивый статус «Офлайн» и число локальных изменений при их наличии.
2. **Given** идёт отправка очереди, **When** пользователь продолжает работать,
   **Then** статус меняется на «Синхронизация», не блокируя интерфейс задач.
3. **Given** пользователь офлайн, **When** он обращается к AI или другой сетевой
   функции, **Then** Glowy спокойно объясняет необходимость подключения и не
   списывает AI-лимит.

### Edge Cases

- Пользователь выходит из аккаунта при наличии локальной очереди: очередь
  сохраняется отдельно для этого аккаунта и не показывается следующему.
- Временная задача создана и удалена до возвращения сети: лишние сетевые
  действия сворачиваются, если это можно сделать без изменения результата.
- Подзадача относится к задаче с временным идентификатором: сначала создаётся
  родительская задача, затем зависимые действия получают серверный идентификатор.
- Браузер сообщает `online`, но сервер недоступен: состояние считается ошибкой
  синхронизации, а не успешным подключением.
- В двух вкладках есть одна очередь: только одна вкладка выполняет действие в
  конкретный момент, а обе получают актуальное локальное состояние.
- Пользователь очищает данные браузера: локальные несинхронизированные изменения
  могут быть потеряны; интерфейс не обещает обратного.
- Сервер принял действие, но ответ потерялся: клиент сохраняет действие до
  подтверждения и предупреждает о возможном конфликте; полная серверная
  идемпотентность требует отдельного согласованного backend-контракта.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST хранить локальный снимок задач и подзадач отдельно для
  каждого авторизованного пользователя.
- **FR-002**: Система MUST открывать последний локальный снимок после
  перезагрузки без сети, если пользователь ранее загрузил его на устройстве.
- **FR-003**: Пользователь MUST иметь возможность создавать, изменять, завершать и
  удалять задачи и подзадачи без подключения.
- **FR-004**: Каждое локальное изменение MUST сохраняться в устойчивой очереди
  до подтверждённой отправки на сервер.
- **FR-005**: Система MUST применять локальное действие к интерфейсу сразу, не
  ожидая сети.
- **FR-006**: Система MUST автоматически запускать синхронизацию после
  восстановления сети и при запуске приложения онлайн.
- **FR-007**: Система MUST обрабатывать очередь в порядке зависимостей и заменять
  временные идентификаторы серверными после успешного создания.
- **FR-008**: Неуспешное действие MUST оставаться в очереди и не приводить к
  удалению следующих несинхронизированных данных.
- **FR-009**: Пользователь MUST видеть состояния «Офлайн», «Сохранено на
  устройстве», «Синхронизация» и «Требуется внимание».
- **FR-010**: Пользователь MUST иметь возможность вручную повторить неуспешную
  синхронизацию.
- **FR-011**: Система MUST предотвращать одновременную обработку одного и того же
  локального действия несколькими вкладками одного браузера.
- **FR-012**: Локальные данные одного аккаунта MUST NOT отображаться другому
  аккаунту на том же устройстве.
- **FR-013**: Выход из аккаунта MUST NOT молча удалять несинхронизированную
  очередь; после повторного входа того же пользователя она должна быть доступна.
- **FR-014**: AI, платежи, вход, восстановление доступа и другие сетевые функции
  MUST оставаться недоступными офлайн с понятным объяснением.
- **FR-015**: Offline-режим MUST NOT хранить пароли, платёжные данные, ключи
  провайдеров или необработанный AI-контент в локальном хранилище задач.
- **FR-016**: Гостевой режим MUST сохранить текущее локальное поведение и не
  отправлять данные на сервер.
- **FR-017**: Обновление приложения MUST сохранять совместимые локальные данные
  и очередь либо показывать понятное состояние при несовместимости.

### Key Entities

- **Локальный снимок задач**: Последнее известное состояние задач и подзадач
  конкретного пользователя на устройстве.
- **Локальное действие**: Намерение пользователя создать, изменить, завершить
  или удалить задачу/подзадачу; содержит тип, полезные данные, зависимости,
  время создания, число попыток и статус.
- **Временный идентификатор**: Локальный идентификатор новой сущности до ответа
  сервера, позволяющий связывать последующие действия.
- **Состояние синхронизации**: Общий статус очереди, количество ожидающих
  действий, последняя успешная отправка и безопасная информация об ошибке.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: После одного успешного онлайн-сеанса пользователь открывает список
  задач без сети и видит локальные данные не позднее чем через 2 секунды.
- **SC-002**: 100% поддержанных действий с задачами и подзадачами сохраняются
  после перезагрузки страницы без сети.
- **SC-003**: После восстановления стабильной сети очередь из 20 действий
  начинает обрабатываться не позднее чем через 3 секунды и завершается без
  потери локального результата.
- **SC-004**: В интерфейсе всегда можно определить один из четырёх статусов:
  офлайн, сохранено локально, синхронизация или требуется внимание.
- **SC-005**: Автоматические проверки подтверждают открытие кэша, сохранение
  очереди, восстановление после перезагрузки, успешную синхронизацию и повтор
  после ошибки.
- **SC-006**: При смене аккаунта на одном устройстве в тестах не отображаются
  задачи или очередь предыдущего пользователя.

## Assumptions

- v2.6.0 покрывает задачи и подзадачи. Привычки, заметки и серверная история AI
  не входят в этот релиз и оцениваются отдельно после подтверждения сценария.
- Пользователь уже авторизовался на устройстве до потери сети; новый вход и
  регистрация требуют подключения.
- Текущий backend API задач переиспользуется без Prisma migration.
- Базовое разрешение конфликтов в этом релизе: серверный снимок загружается, а
  подтверждённые локальные действия воспроизводятся поверх него по очереди.
- Полная гарантия «ровно один раз» между устройством и сервером потребует
  серверных idempotency keys и отдельного согласования; v2.6.0 обеспечивает
  устойчивую клиентскую очередь и защиту от параллельной обработки в браузере.
- Интерфейс приложения уже может открываться после первого посещения благодаря
  существующему app shell; релиз расширяет это поведение данными и изменениями.
