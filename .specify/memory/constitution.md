# Конституция Glowy

## Основные принципы

### I. Пользовательская ценность и контроль
Glowy ОБЯЗАН помогать человеку спокойно понять, что делать дальше, учитывая его задачи
и энергию. AI может предложить ответ, объяснение или черновик, но НЕ МОЖЕТ без ведома
пользователя создавать, менять, завершать, удалять, публиковать или передавать его данные.
Любое значимое действие AI требует явного подтверждения пользователя и должно иметь
понятный, обратимый результат.

Обоснование: отличие продукта -- поддерживающее планирование, а не лишение человека
контроля над его делами.

### II. Развитие существующей архитектуры
Новая работа ОБЯЗАНА переиспользовать существующие frontend-, backend-, API-, AI-, auth-
и payment-flow, если они удовлетворяют задаче. Запрещено создавать параллельные механизмы
оплаты, сессий, AI или базы данных без явного архитектурного решения с объяснением причины.
Изменения ОБЯЗАНЫ оставаться узкими по области; несвязанные рефакторинги нельзя добавлять
в feature или bug fix.

Обоснование: Glowy развивается из MVP, поэтому последовательность и безопасные малые шаги
ценнее новой архитектуры ради самой архитектуры.

### III. Защита данных, денег и секретов
Проверка доступа, тарифные лимиты, учёт AI-запросов, состояние платежа и верификация
провайдера ОБЯЗАНЫ выполняться на backend; клиент никогда не является источником истины.
Секреты ОБЯЗАНЫ храниться только в переменных окружения и НЕ ДОЛЖНЫ попадать в git, логи
или браузер. Логи НЕ ДОЛЖНЫ содержать пользовательские тексты, промпты, токены, пароли
и другие персональные данные.

Изменение схемы базы или production migration требует явного согласования с пользователем
и подтверждённого backup Timeweb до выполнения. В production ЗАПРЕЩЕНО использовать
`prisma migrate reset` или `prisma db push` для исправления базы. Backend ОБЯЗАН
переиспользовать общий Prisma client, а не создавать отдельные клиенты или connection pool.
Новые и изменённые подключения к базе ОБЯЗАНЫ проверять TLS-сертификат.

Изменения оплаты ОБЯЗАНЫ сохранять проверку платежа через провайдера, ожидаемой суммы,
валюты и метаданных, а также идемпотентную обработку webhook до активации тарифа.

Обоснование: ошибка здесь может раскрыть личные данные, повредить существующую базу
пользователей и задач или неверно выдать платный доступ.

### IV. Доказательства перед релизом
Каждое изменение ОБЯЗАНО иметь проверку, соразмерную риску. Для UI-изменений нужны
релевантные build, lint или type checks и ручная проверка сценария. Изменения общих
контрактов, AI, auth, payment, лимитов, данных и мобильных сценариев требуют целевых
автоматизированных тестов, когда это возможно, плюс end-to-end или ручного сценария
изменённого flow. Упавшая релевантная проверка ДОЛЖНА быть исправлена либо явно описана
как известный риск; её нельзя молча игнорировать.

Обоснование: у продукта есть реальные пользователи, production-инфраструктура и платежи;
уверенность должна опираться на проверку, а не только на успешное изменение кода.

### V. Понятная совместная разработка
Код, API-контракты, конфигурация, release notes и operational-инструкции ОБЯЗАНЫ оставаться
понятными будущему разработчику и AI-агенту. Используй принятые в репозитории соглашения,
точные типы и валидацию на границах, а комментарии оставляй только для неочевидных решений.
Пользовательский текст ОБЯЗАН быть на русском языке, пока функция явно не вводит локализацию.

Каждый commit ОБЯЗАН быть сфокусированным, описывать фактическое изменение и не включать
несвязанные пользовательские правки. Документация ОБЯЗАНА обновляться, когда существенно
меняются публичное поведение, конфигурация, deploy, оплата, AI или продуктовый план.

Обоснование: Glowy развивается совместно и нуждается в сохраняющемся контексте между
устройствами, участниками и будущими релизами.

## Архитектурные границы

- Текущий продукт -- React + TypeScript на frontend, Express + strict ESM TypeScript на backend,
  Prisma и PostgreSQL. Backend source компилируется в `backend/dist/`. Сохраняй существующие
  границы ответственности, если specification явно не утверждает их изменение.
- Используй единственный Prisma instance из source-файла `backend/lib/prisma.ts`. В NodeNext
  TypeScript его import specifier может заканчиваться на emitted `.js`; это не разрешение создавать
  JavaScript-версию, второй `PrismaClient` или raw database pool.
- Считай существующую Timeweb PostgreSQL базу, её пользователей, задачи, подзадачи и платежи
  живыми данными. Предпочитай аддитивные, обратно совместимые изменения и документируй
  переход данных и путь отката.
- Вызовы AI-провайдеров проходят через существующий server-side provider/proxy layer.
  Сохраняй лимиты, мягкие сообщения при ошибках и правило: учётные данные провайдера никогда
  не попадают в клиентский код.
- Изменения подписок и оплаты используют существующий YooKassa checkout и webhook flow.
  Изменение цены или политики тарифов должно описывать путь для уже существующих пользователей.
- Landing page можно менять только по явному продуктовому запросу. Не изменяй его попутно
  во время работы над аккаунтом, задачами, AI или оплатой.

## Процесс разработки

1. До редактирования классифицируй работу. Небольшие copy, style, docs или изолированный
   bug fix проходят обычный процесс inspect -> implement -> verify. Новая пользовательская
   функция или изменение нескольких модулей, данных, AI, auth, payment либо deploy ОБЯЗАНО
   идти через Spec Kit.
2. Для работы через Spec Kit создай specification командой `$speckit-specify`, устрани
   существенные неоднозначности через `$speckit-clarify`, спроектируй решение через
   `$speckit-plan`, создай задачи через `$speckit-tasks`, проверь согласованность
   `$speckit-analyze`, затем реализуй `$speckit-implement`. Для крупной функции после
   реализации используй `$speckit-converge`.
3. До любого изменения файлов объясняй планируемую правку. Сначала изучай относящийся к делу
   код и не повторяй широкое исследование репозитория, уже выполненное в рамках той же задачи.
4. До production deploy, migration, forceful git operation, разрушительной команды или
   активации оплаты получай явное согласие пользователя. Простыми словами объясняй команду,
   её эффект, способ проверки и путь восстановления.
5. Завершай работу релевантными проверками, коротким diff summary, известными рисками или
   пропущенными проверками и создавай сфокусированный commit только по запросу пользователя.

## Управление правилами

Эта конституция управляет specification, планами, задачами, code review, инструкциями для
агентов и release-работой в репозитории Glowy. Если задача противоречит правилу с ОБЯЗАНО,
задачу нужно исправить либо сначала явно изменить конституцию.

Поправка требует записать причину, обновить этот документ и применить semantic versioning:
MAJOR для удаления или несовместимого изменения принципов, MINOR для нового или существенно
расширенного принципа и PATCH для уточнения формулировок. Каждый существенный feature plan
и review ОБЯЗАН проверять соответствие этим принципам. Практические инструкции в `README.md`,
`docs/` и будущем `AGENTS.md` могут добавлять детали, но не могут ослаблять конституцию.
