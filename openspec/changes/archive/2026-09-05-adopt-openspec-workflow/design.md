## Context

См. мотивацию в `proposal.md`. Сейчас обязательные правила находятся в
`.specify/memory/constitution.md` и `AGENTS.md`, а история функций — в 24 каталогах `specs/`.
Эти артефакты полезны как журнал решений, но не образуют актуальную модель продукта. В корне уже
есть несколько независимых Node.js-проектов; OpenSpec нужен только как devDependency главного
проекта и не должен попадать в production runtime.

Миграция не меняет код приложения, данные, API или deployment. Исторические документы сохраняют
смысл на дату создания, поэтому их нельзя массово переписывать под новый workflow.

## Goals / Non-Goals

**Goals:**

- сделать запуск OpenSpec воспроизводимым из репозитория без глобальной установки;
- дать агенту один краткий project context и обязательные правила для каждого нового change;
- сформировать проверяемый baseline текущих продуктовых возможностей;
- сохранить трассировку от старых release-oriented specs к новым capability-oriented specs;
- определить один активный lifecycle изменения и чёткую границу между планированием и apply;
- обеспечить безопасный откат tooling-миграции обычным git revert.

**Non-Goals:**

- менять пользовательское поведение, runtime-зависимости, API или схему данных;
- переписывать или архивировать задним числом исторические Spec Kit-артефакты;
- переносить незавершённые идеи roadmap в baseline как уже существующие requirements;
- внедрять TanStack Query, дизайн-систему или другие задачи v3.0.0 в этом change;
- выполнять push, deploy или любые операции с production.

## Decisions

### 1. Закрепить OpenSpec как локальную devDependency

Используем точную версию `@fission-ai/openspec` и npm scripts для status/strict validation. Это
даёт одинаковый CLI локально и в CI и исключает зависимость от глобального окружения. Альтернатива
с глобальной установкой отклонена как невоспроизводимая; плавающая версия отклонена из-за риска
самопроизвольного изменения форматов.

### 2. Организовать specs по устойчивым возможностям, а не по релизам

Начальный baseline разбивается на домены: account/auth, tasks/subtasks, AI assistant,
notes, progress/analytics, offline sync, Telegram, subscriptions/payments и platform quality.
Каждый `openspec/specs/<capability>/spec.md` фиксирует только проверенное текущее поведение через
Requirements и Scenarios. Будущие идеи остаются в roadmap до отдельного change.

Альтернатива «один spec на весь продукт» отклонена как плохо рецензируемая. Копирование всех 24
старых каталогов один-в-один отклонено, потому что оно сохранит release-oriented дублирование и
не создаст канонический baseline.

### 3. Сохранить старую систему как read-only исторический слой

`.specify/` и корневые `specs/001-*`…`specs/024-*` остаются в git и получают явную пометку
исторического источника. Активные инструкции Spec Kit удаляются из `.agents/skills`, чтобы агент
не выбирал два конкурирующих workflow. Трассировка старых каталогов на новые capabilities
фиксируется в `openspec/MIGRATION.md`.

### 4. Оставить конституцию независимым верхнеуровневым контрактом

`.specify/memory/constitution.md` сохраняет путь ради совместимости ссылок, но её process-раздел
переводится на OpenSpec и версия повышается по собственным правилам документа. `openspec/config.yaml`
получает сжатый operational context и не дублирует конституцию целиком. При конфликте конституция и
`AGENTS.md` остаются обязательными, а change-артефакт должен быть исправлен.

### 5. Использовать lifecycle explore → propose → review → apply → verify → archive

`explore` остаётся read-only исследованием. `propose` создаёт proposal/design/tasks и delta-specs,
но не разрешает реализацию в том же workflow. После review пользователь явно запускает apply.
`verify` сверяет код, сценарии и задачи до archive; archive обновляет канонические specs.
`sync-specs` допускается только для осознанного переноса дельт до archive, а `update-change` — для
изменения уже созданных артефактов.

Альтернатива автоматического propose+apply отклонена: она убирает точку review и особенно опасна
для auth, payment, AI и data-изменений.

### 6. Обновлять только живые инструкции

Меняются `AGENTS.md`, onboarding, актуальный handoff, next-chat prompt, architecture, roadmap и
индекс документации. Датированные handoff до 2026-09-04 и release/spec history не переписываются;
ссылки на Spec Kit в них остаются исторически корректными.

## Risks / Trade-offs

- [Baseline может ошибочно выдать старую задумку за реализованное поведение] → сверять каждый
  requirement с кодом, тестами, актуальной архитектурой и handoff; сомнительное не включать.
- [Два дерева specs временно усложняют поиск] → добавить карту миграции и назвать OpenSpec
  единственным активным источником, а старое дерево — историческим.
- [Обновление CLI может изменить сгенерированные skills] → закрепить точную версию, обновлять
  осознанным отдельным change и проверять diff.
- [OpenSpec добавляет заметный объём в lockfile и audit findings] → держать пакет только в
  devDependencies, отдельно проверить production dependency tree и зафиксировать результат без
  автоматического `audit fix`.
- [Ручная синхронизация config, AGENTS и конституции может расходиться] → описать и проверить
  иерархию источников; включить документы в одну задачу и strict validation gate.

## Migration Plan

1. Закрепить CLI, сгенерировать OpenSpec skills и настроить project context/rules.
2. Создать capability baseline и карту происхождения требований.
3. Перевести живые инструкции и конституцию на новый lifecycle.
4. Удалить только активные Spec Kit skills, сохранив `.specify/` и исторические specs.
5. Выполнить strict OpenSpec validation, project checks и review diff.
6. После успешной реализации проверить change через verify и только затем архивировать.

Rollback выполняется revert-ом migration commit: runtime и база данных не затрагиваются. При
частичном откате нельзя удалять исторические specs; OpenSpec dependency, config, skills и новые
docs следует откатывать согласованно.
