# Feature Specification: Quality Baseline v2.1.0

**Feature Branch**: `codex/v2.1.0-quality-baseline`

**Created**: 2026-08-07

**Status**: Draft

**Input**: User description: "Выпустить v2.1.0 как Quality Baseline: укрепить качество,
тестирование, наблюдаемость, измерения и документацию Glowy перед следующими крупными
AI-функциями."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Надёжно пользоваться основными сценариями (Priority: P1)

Пользователь открывает Glowy на компьютере или телефоне, может перейти к регистрации и
пользоваться уже существующими критическими экранами, не теряя доступ ко всему приложению
из-за ошибки в одном из них.

**Why this priority**: Перед привлечением новых пользователей базовые сценарии должны быть
стабильнее новых возможностей.

**Independent Test**: На desktop и мобильном размере экрана открыть публичный вход, пройти
критический пользовательский сценарий и убедиться, что локальная ошибка экрана даёт понятное
восстановление вместо пустой страницы приложения.

**Acceptance Scenarios**:

1. **Given** пользователь открывает публичный адрес Glowy, **When** страница загружается на
   desktop или телефоне, **Then** он видит понятную точку входа и может перейти к регистрации.
2. **Given** ошибка возникает внутри ограниченной части приложения, **When** пользователь
   остаётся на странице, **Then** остальной интерфейс не становится недоступным и показывается
   понятное действие для восстановления.

---

### User Story 2 - Получать прозрачный путь от рекламы до первого действия (Priority: P2)

Пользователь приходит по рекламной или контентной ссылке, даёт согласие на аналитику и может
без скрытого сбора личных данных пройти регистрацию, создать первую задачу и использовать AI.

**Why this priority**: Команде нужны измеримые данные о том, приводит ли трафик к полезному
началу работы, а не только к просмотру лендинга.

**Independent Test**: Пройти сценарий с UTM-меткой и согласием на аналитику, проверить
корректные события в инструменте аналитики и отсутствие событий после отказа от аналитики.

**Acceptance Scenarios**:

1. **Given** пользователь согласился на аналитику и пришёл по размеченной ссылке, **When** он
   начинает и завершает регистрацию, создаёт первую задачу или отправляет первый AI-запрос,
   **Then** соответствующие события доступны в аналитике без содержимого задач, переписки,
   токенов или иных секретов.
2. **Given** пользователь не дал согласие на аналитику, **When** он пользуется авторизованной
   частью приложения, **Then** продуктовые события не отправляются.

---

### User Story 3 - Выпускать изменения с предсказуемой проверкой (Priority: P3)

Разработчик до слияния или релиза получает единый результат обязательных проверок и может
понять, какой пользовательский сценарий сломан, не проверяя весь интерфейс вручную.

**Why this priority**: Это снижает вероятность вернуть уже исправленную ошибку в последующих
версиях, особенно при работе несколькими AI-агентами.

**Independent Test**: Изменить код в изолированной ветке, запустить обязательный набор проверок
и убедиться, что сбой содержит воспроизводимый отчёт.

**Acceptance Scenarios**:

1. **Given** в ветке есть изменение приложения, **When** запускается проверка качества, **Then**
   проверяются типы, стиль кода, unit-сценарии, сборка и ключевой пользовательский путь на
   desktop и мобильном размере экрана.
2. **Given** проверка пользовательского пути не прошла, **When** разработчик открывает результат
   проверки, **Then** ему доступен отчёт, достаточный для воспроизведения причины.

### Edge Cases

- Пользователь открывает приложение при временно недоступном API или при ошибке отдельного
  экрана: он получает понятный интерфейс восстановления, а не бесконечную загрузку или пустой
  экран.
- Аналитика или внешний счётчик недоступны: основные сценарии Glowy продолжают работать.
- UTM-параметры отсутствуют, повреждены или повторно открыты: регистрация и создание задач не
  блокируются, а источник не подменяет данные уже начатой сессии.
- Автоматизированный браузерный сценарий завершается ошибкой: результат содержит достаточные
  диагностические данные, но не секреты и не личные тексты пользователя.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST сохранять доступность остальных частей приложения при непредвиденной
  ошибке в ограниченном пользовательском экране и показывать понятный путь восстановления.
- **FR-002**: Система MUST иметь автоматизированную проверку публичного входа на desktop и
  мобильном размере экрана.
- **FR-003**: Система MUST выполнять обязательные проверки типов, стиля кода, unit-сценариев,
  сборки и ключевых браузерных сценариев до выпуска изменения.
- **FR-004**: При провале браузерного сценария система MUST сохранять диагностический отчёт,
  достаточный для воспроизведения ошибки, без секретов и личного содержимого пользователя.
- **FR-005**: Система MUST фиксировать согласованные продуктовые события, уже доступные в
  v2.1.0: клик одобренного основного CTA, начало и завершение регистрации, первую созданную
  задачу, первый AI-запрос и начало оформления Focus. Имя `ai_draft_confirmed` резервируется
  для v2.2.0 и не является требованием текущего релиза.
- **FR-006**: События из авторизованной части MUST отправляться только после явного согласия
  пользователя на аналитику; отказ не должен ограничивать основные функции Glowy.
- **FR-007**: Аналитика и диагностические записи MUST исключать пароли, токены, секреты,
  содержимое задач, сообщений и голосовых записей.
- **FR-008**: Для ошибок backend-критичных сценариев MUST быть доступна структурированная запись
  причины и контекста запроса, достаточная для расследования без раскрытия секретов.
- **FR-009**: Публичные обещания лендинга MUST соответствовать фактически доступным сценариям;
  изменения лендинга ограничиваются исправлением несоответствий и измеримостью CTA, без
  редизайна.
- **FR-010**: Документация MUST описывать текущую границу frontend, backend, базы данных,
  AI-сервиса и платежей, а также критерии готовности релиза и безопасные действия перед
  production-изменениями.

### Key Entities *(include if feature involves data)*

- **Product analytics event**: обезличенная запись о согласованном действии пользователя,
  содержащая название события, момент действия и разрешённые параметры источника перехода.
- **Quality check result**: результат автоматизированной проверки с именем сценария, статусом и
  диагностическими материалами при ошибке.
- **Structured error record**: диагностическая запись о сбое критичного серверного сценария без
  секретов и личного пользовательского содержимого.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Обязательный набор проверок завершается успешно на чистой ветке v2.1.0 и включает
  проверку типов, lint, unit-тесты, production-сборку и браузерный smoke-сценарий для двух
  размеров экрана.
- **SC-002**: Публичный вход и ссылка регистрации проходят автоматически на desktop и мобильном
  размере экрана.
- **SC-003**: Для каждого реализованного в v2.1.0 события в тестовом сценарии аналитики
  существует ровно одно понятное имя события, а в его данных отсутствуют личные тексты и
  секреты.
- **SC-004**: При отказе от аналитики авторизованный пользователь может выполнить основной
  сценарий без отправки продуктовых событий.
- **SC-005**: В документации v2.1.0 есть архитектурная схема и release checklist, по которым
  другой разработчик может подготовить проверку и выпуск без обращения к истории чата.

## Assumptions

- Существующие auth, tasks, AI и YooKassa flows сохраняются; v2.1.0 не добавляет параллельную
  архитектуру и не меняет тарифные правила.
- Внешний сервис мониторинга не подключается без отдельного решения по поставщику и учётным
  данным. В v2.1.0 достаточно улучшить локально доступные диагностические записи и error states.
- Изменения схемы базы данных, production-миграции, включение оплаты и deployment требуют
  отдельного подтверждения пользователя и не являются автоматической частью этой спецификации.
- AI Task Builder, голосовой ввод, история диалогов и новая мобильная навигация относятся к
  v2.2.0 и не входят в v2.1.0.
- Backend API-тесты используют только изолированное тестовое окружение; production-база Timeweb
  никогда не применяется для тестов.
